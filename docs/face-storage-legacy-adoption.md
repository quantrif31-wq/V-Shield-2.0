# Legacy face model adoption

Legacy face models are not authoritative identity records. A filename such as
`emp_1_...pkl` supplies only `suggestedEmployeeId=1`; it never supplies the
official `employeeId`. An operator must review and approve every mapping before
any file or database row can be created.

The current audited database contains no `EmployeeFaceModels` rows, so the five
legacy files remain `Orphaned`. Do not backfill them in an EF migration.
Adoption is an explicit operational action performed before canonical model
storage cutover. Enrollment jobs and model lifecycle versioning are not yet
implemented.

## Prerequisites

- Use a trusted Python environment containing the dependencies in
  `AI_Runtime/face_recognition/requirements.txt`.
- Supply the SQL Server connection through
  `VSHIELD_FACE_ADOPTION_CONNECTION_STRING`; never put it in a manifest or
  command history.
- Keep `FACE_MODEL_DIR` on the legacy model directory throughout adoption.
- Confirm `runtime/face-data/models/active`, `staging`, `archive`, and `failed`
  are on one filesystem.
- Keep `API/API/API/wwwroot/uploads/VideoFace/FaceID` unchanged as the rollback
  source.

## 1. Generate an unapproved template

```powershell
python scripts/adopt_legacy_face_models.py --generate-template
```

The ignored template is written to
`runtime/face-data/manifests/legacy-face-model-adoption.json`. Generation
calculates checksums and encoding counts but leaves:

```json
{
  "approved": false,
  "approvedBy": "",
  "approvedAtUtc": null,
  "models": [
    {
      "fileName": "example.pkl",
      "suggestedEmployeeId": 1,
      "employeeId": null,
      "expectedSha256": "<sha256>",
      "expectedEncodingCount": 1
    }
  ]
}
```

An authorized operator must fill every `employeeId`, review any difference from
the suggested ID, set `approved=true`, name the approver, and set a UTC ISO 8601
approval timestamp. The script never copies `suggestedEmployeeId` into
`employeeId`.

## 2. Validate without mutation

Running without a mode is validation/dry-run:

```powershell
python scripts/adopt_legacy_face_models.py
```

`--validate` is equivalent. Validation requires exactly one approved entry per
source model, unique filenames and employee IDs, valid source checksum and
encoding count, an existing employee, no ambiguous `EmployeeFaceModels` row,
and a non-conflicting destination. A deliberate mapping that differs from the
filename suggestion is blocked by default and additionally requires
`--allow-filename-mismatch`.

Validation does not insert rows or copy files. Reports contain IDs, filenames,
checksums, counts, statuses, and warnings only—never encodings, credentials, or
personal employee data.

## 3. Apply all mappings atomically

Apply requires both an approved manifest and an explicit confirmation:

```powershell
python scripts/adopt_legacy_face_models.py --apply --confirm-adoption
```

If a reviewed mapping differs from its filename suggestion, also provide
`--allow-filename-mismatch`. Apply is all-or-nothing:

1. Copy every source into a temporary file on the canonical active filesystem.
2. Flush and verify checksum and encoding count before publication.
3. Publish files atomically without changing the legacy source.
4. Insert every `EmployeeFaceModels` row in one SQL transaction.
5. Store `ModelPath` as `models/active/<basename>`.
6. Store the UTC adoption time in `CreatedAt`. It is not the original training
   timestamp.

If file preparation or database commit fails, newly published files are removed
only when their checksums still match. Pre-existing identical destination files
are never deleted. Database failure is rolled back and a failure/rollback
manifest is written to the ignored manifests directory.

A successful rerun validates the same database row and destination checksum,
returns `AlreadyAdopted`, preserves `CreatedAt`, and creates no duplicate.

## 4. Rollback

Rollback defaults to dry-run and requires the rollback manifest generated by
the corresponding apply:

```powershell
python scripts/adopt_legacy_face_models.py `
  --rollback runtime/face-data/manifests/<rollback-manifest>.json
```

Actual rollback requires confirmation that Face Runtime is still using legacy
storage or has already been restored to it:

```powershell
python scripts/adopt_legacy_face_models.py `
  --rollback runtime/face-data/manifests/<rollback-manifest>.json `
  --confirm-rollback `
  --runtime-restored-to-legacy
```

Rollback verifies database row identity and destination checksums, deletes only
rows and files created by that adoption run, and never changes employees,
videos, pre-existing destination files, the legacy source, or
`FACE_MODEL_DIR`.

## Cutover remains separate

Adoption does not reload or restart Face Runtime. After adoption, run inventory
again and require all five models to be `Ready`, then separately perform the
verified canonical storage cutover. Physical RTSP camera connectivity is not
accepted by this procedure.
